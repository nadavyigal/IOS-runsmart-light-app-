# RunSmart 1.1.6 (31) Release Plan

**Status:** PR #136 merged as `e910a5c`; the 1.1.6 (31) candidate passed tests, Release simulator/device compilation, bundle inspection, and the guest-value simulator smoke on `codex/runsmart-1.1.6-build31`. It is ready to land and archive interactively in Xcode; upload/submission remain gated below.

**Public baseline:** 1.1.5 (30), released 2026-08-05.

**Release source baseline:** `origin/main` at `e910a5c` (RunSmart iOS PR #136).

**Target:** 1.1.6 (31). The founder confirmed in App Store Connect on 2026-08-13 that build 31 is unused.

**Release objective:** ship the native auth-return repair, activation measurement foundation, and a reversible guest journey that delivers a personalized Week 1 preview before account creation.

## Decision

Treat 1.1.6 as a **reliability plus activation release**. It carries the measurement foundation and one founder-directed product bet: value before authentication.

The marketing version should move from 1.1.5 to 1.1.6 because the candidate changes real authentication behavior: an iOS-originated email/browser round trip can return to a native RunSmart session. Build 31 is the expected next build after public build 30, but must be checked in App Store Connect before editing the project.

The earlier evidence gate for WP-61b was deliberately overridden by the founder on 2026-08-13. The guest path remains isolated behind `RUNSMART_GUEST_MODE_ENABLED`, stores answers only on the device until authentication, and can be removed from the entry route with one configuration change. Do not bundle Garmin commercial work, voice coach changes, monetization, localization, route redesign, or other product work into this release.

## Landing and Effectiveness Plan

### Before Release

Save/freeze both ordered, session-scoped paths split by `app_build`.

Direct auth:

`app_launched → activation_first_frame_rendered → sign_in_wall_reached → sign_in_completed → onboarding_completed → plan_generation_succeeded → first_workout_viewed → run_started → run_completed`

Guest value:

`app_launched → activation_first_frame_rendered → sign_in_wall_reached → guest_mode_started → guest_profile_completed → guest_plan_preview_viewed → guest_sign_in_prompted → sign_in_completed → guest_authenticated_upgrade → onboarding_completed → plan_generation_succeeded → first_workout_viewed → run_started → run_completed`

Keep exclusions for internal tester, emulator, sideload, TestFlight, and known App Store Review traffic. Record implementation birthdays separately from production first-seen.

### First Production Event

- [ ] Confirm build 31 emits `app_launched`, `activation_first_frame_rendered`, and `sign_in_wall_reached` in one external session and in that order.
- [ ] Confirm `entry=cold_launch` on first reach and stable `screen=sign_in_wall`.
- [ ] Confirm event and identified-person `is_internal_tester` values behave as designed.
- [ ] Confirm no new permission request is left without a granted/denied/dismissed/failed terminal.
- [ ] Confirm the native callback path can produce `sign_in_completed(method=email)` when exercised.
- [ ] Confirm the guest event sequence is ordered and that authentication joins the anonymous pre-auth journey to the identified user.

### T+1 and Sample Gate

Run a T+1 health check only if external build-31 traffic exists; otherwise wait for the first genuine event and report “no cohort,” not zero conversion.

Do not call the guest path effective from simulator success or isolated anecdotes. At n≥10 eligible external users at each examined step:

1. Report counts and conversion at each launch-to-wall step, not percentages alone.
2. Separate cold launch, warm foreground, and background-return wall entries.
3. Report pre-auth screen dismissals and permission outcomes by kind.
4. Compare qualifying launch → `guest_plan_preview_viewed` and preview → authenticated upgrade against the frozen pre-release baseline, with counts and p50/p75 time to preview.
5. Keep the feature if it increases first-value exposure without reducing downstream onboarding completion or first-workout/run commitment; otherwise disable the flag and inspect the largest measured loss.

## Rollback / Stop Conditions

- If archive or device auth verification fails, do not upload; keep 1.1.5 live.
- If TestFlight cannot return from the canonical Universal Link, stop and fix the AASA/redirect allowlist before submission.
- If a release-build auth or run-recording crash appears, reject the candidate and cut a corrected build number; never reuse build 31 after upload.
- If production telemetry is absent but the build has genuine launches, treat it as an instrumentation incident before interpreting activation.
- If production auth regresses, halt distribution and restore the last known-good path before running activation experiments.

## Explicitly Out of Scope

- New onboarding, route, Garmin, coach, monetization, localization, or paywall features.
- Resumely changes or any mutation to Resumely 1.4.9 while it is under App Store review.
- App Store upload/submission in the planning session.
